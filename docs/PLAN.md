# Qazaq Loc QA: план и документация

Oct 30, 2026 · @Adilkhan

## 1. Цель и результат сдачи

Мы делаем на Python CLI-инструмент `locqa`, который сравнивает русский ARB-файл с казахским и выдаёт структурированный список ошибок. Большую часть проверок делает код по правилам, а LLM берёт только то, что правилами не поймать, и предлагает исправления. Исправленный казахский файл подтверждает носитель языка.

Свою модель мы не обучаем: для этого нет размеченных данных, а правила надёжнее модели в проверках формата. Качество казахского в LLM-части обеспечиваем глоссарием, примерами от носителя и контекстом в промпте.

**Что сдаём**

- CLI: `locqa check --source intl_ru.arb --target intl_kk.arb --glossary glossary.csv --out report.json`
- `report.json` и человекочитаемый HTML-отчёт
- `glossary.csv`: термины на ru, kk, en с комментариями по употреблению
- `intl_kk_fixed.arb`: у каждой изменённой строки отметка, проверил ли её человек
- описание методологии: как искали, как исправляли, сколько строк прошло через носителя
- в отчёте стоимость обработки через LLM

**Как оценивают**

| Критерий | Как измеряют | Вес |
| --- | --- | --- |
| Детекция подложенных ошибок | Recall по \~100 подложенным ошибкам с учётом типа. Precision по ручной проверке 100 случайных находок | 35% |
| Качество исправлений | Носители вслепую сравнивают исправленный и исходный вариант на 150 случайных изменённых строках | 35% |
| Универсальность | Работает на любом ARB без правок, есть документация и тесты | 15% |
| Объяснимость | У каждой находки понятные evidence и severity, мало шума | 15% |

Из таблицы следуют три правила. Шум в отчёте снижает оценку. Массовая замена через LLM без проверки человеком снижает оценку. Строки без отметки проверки в оценку качества не идут.

## 2. Структура репозитория и данные

Стартового репозитория нет, начинаем с пустого приватного. Данные организаторов лежат в `data/` и закрыты в `.gitignore`, даже пока репозиторий приватный. Тогда его можно открыть в любой момент без утечки.

```
qazaq-loc-qa/
  README.md
  pyproject.toml
  .gitignore              # data/, out/, .env
  docs/
    task.pdf              # PDF кейса
    PLAN.md  SCHEMA.md  METHODOLOGY.md
  data/                   # НЕ в git: intl_ru/kk/uz/en.arb
  glossary/glossary.csv
  src/locqa/
    cli.py                # точка входа, команды
    models.py             # Finding, Severity, IssueType
    arb/  parser.py  writer.py
    checks/               # по одному файлу на проверку
    glossary.py
    llm/  client.py  prompts/  cost.py  cache.py
    report/  json_writer.py  html_writer.py  templates/
    fix/  review_sheet.py  apply.py  validate.py
  tests/
    fixtures/             # маленькие синтетические ARB, в git
  .github/workflows/check.yml
  out/                    # не в git: report.json, report.html, cost.json
```

**Правила работы с данными (условия организаторов)**

- данные только для кейса в рамках Decentrathon 6.0
- не пытаться деанонимизировать игроков, устройства и адреса
- не публиковать данные и производные выборки, в том числе в публичных репозиториях; репозиторий с кодом может быть публичным
- удалить данные в течение 14 дней после объявления победителей
- тестовые фикстуры пишем сами, по форме похожие на реальные файлы, но не копируем строки из `data/`
- LLM API получает строки из `data/` только как часть работы кейса; ключи API хранятся в `.env`, не в git

## 3. Архитектура и поток данных

Программа работает как конвейер: каждый шаг принимает данные от предыдущего и не знает про соседние. Так роли в команде не мешают друг другу, а общий договор у всех один: формат `Finding` (раздел 4).

1. **Чтение ARB** (`arb/parser.py`). Построчный разбор, потому что `"@@comment"` повторяется и обычный `json.load` оставит только последний. На выходе словарь `ключ -> запись` (значение, номер строки, раздел из `@@comment`, метаданные `@key`) и список дублей ключей.
2. **Выравнивание**. Для каждого ключа собираем пару `source` + `target` (и по желанию `en`, `uz` как дополнительный контекст для LLM). Ключи, которых нет в одном из файлов, помечаем сразу.
3. **Правила** (`checks/`). Каждая проверка это отдельный класс с одним методом `run(pairs, ctx) -> list[Finding]`. Реестр проверок позволяет включать и отключать их флагом `--only` / `--skip`.
4. **Фильтр для LLM**. Дальше идут только строки, которые правила не смогли решить: спорные `same_as_source`, подозрительные по эвристикам на машинный перевод, строки с уже найденными проблемами, для которых нужно `suggestion`. Весь файл в LLM не отправляем.
5. **LLM-слой** (`llm/`). Пачки строк, структурированный JSON-ответ, кеш, подсчёт стоимости. Результат: такие же `Finding`, только с полем `suggestion`.
6. **Сборка отчёта** (`report/`). Слияние находок, удаление дублей (один ключ + один тип = одна находка), сортировка по severity, запись `report.json`, `report.html`, `cost.json`.
7. **Таблица для носителя** (`fix/review_sheet.py`). Выгрузка находок с `suggestion` в CSV, где носитель ставит решение по каждой строке.
8. **Применение исправлений** (`fix/apply.py`). В файл попадают только строки, подтверждённые носителем. Файл пишем точечно, без пересборки всего JSON, чтобы не потерять `@@comment`, порядок и экранирование.
9. **Валидация** (`fix/validate.py`). Совпадение плейсхолдеров, корректный ICU, запуск `flutter gen-l10n`.

Три входа и три выхода в целом: на входе ARB-файлы, глоссарий и ключ API; на выходе `report.json` с HTML, `glossary.csv` и `intl_kk_fixed.arb` с флагами проверки.

## 4. Модель данных

Единый объект на всём пути программы есть `Finding`. Его поля совпадают со схемой организаторов, поэтому отчёт не нужно переводить из одного формата в другой.

| Поле | Тип | Что записываем |
| --- | --- | --- |
| `key` | строка | Ключ из ARB, например `garage_rent_button` |
| `issue_type` | перечисление | Один из 11 кодов из раздела 6 |
| `severity` | `high` / `medium` / `low` | Важность: high ломает игру или смысл, low это замечание |
| `source` | строка | Русский оригинал |
| `target` | строка | Текущий казахский перевод (пустой для `untranslated`) |
| `evidence` | строка | Что именно найдено, с числами: «28 символов против 10, ключ похож на кнопку» |
| `suggestion` | строка или null | Предложенный вариант. Для проверок без исправления пусто |
| `confidence` | 0..1 | Для правил из кода фиксированная (например 1.0 для несовпадения плейсхолдеров), для LLM оценка модели |
| `reviewed_by_human` | bool | `false`, пока носитель не подтвердил |

Для внутреннего потребления можно добавить поля `source_of_finding` (`rule` или `llm`) и `check_id`, но в `report.json` лишние поля лучше не писать, пока не уточнили у организаторов, что они терпят.

**Форма `report.json`.** В описании кейса дан пример одной находки, а форма всего файла не описана. Безопаснее всего плоский JSON-массив таких объектов. Сводку (сколько находок по типам, стоимость LLM, версия инструмента) кладём в отдельный `report_meta.json`.

**`glossary.csv`.** Колонки от организаторов: `ru`, `kk`, `en`, `note`. Наши расширения, которые программа может читать: `register` (`literary` или `slang`, нужно для «варн», «мут», «фура», «ГК»), `forbidden_kk` (варианты, которые считаем нарушением) и `severity`. Сленг в оригинале отмечен как предупреждение (warning), а не как ошибка.

**Флаг проверки в `intl_kk_fixed.arb`.** Организаторы требуют отметку у каждой изменённой строки, но не указали формат. Предлагаем два уровня: запись в `@key` (например поле `x-reviewed_by_human: true`) и отдельный файл `fixed_review.json` со списком изменений. Перед выбором нужно проверить, что `flutter gen-l10n` не падает на дополнительном поле в метаданных.

## 5. CLI: команды и коды возврата

Единая точка входа `locqa` с подкомандами. Обязательная по заданию команда одна (`check`). Остальные нужны для работы с носителем и для удобства. Библиотеку для CLI (`typer` или `argparse`) выбирает разработчик, на контракт это не влияет.

| Команда | Вход | Выход | Зачем |
| --- | --- | --- | --- |
| `locqa check` | `--source`, `--target`, `--glossary`, `--out` | `report.json`, `report.html`, `cost.json` | Главная команда из задания |
| `locqa review-sheet` | `report.json` | `review.csv` | Таблица, где носитель принимает или правит исправления |
| `locqa apply` | `--target`, `review.csv` | `intl_kk_fixed.arb`, `fixed_review.json` | Вносит только подтверждённые строки |
| `locqa validate` | `--source`, `--target` | отчёт в консоли, код возврата | Плейсхолдеры, ICU, запуск `flutter gen-l10n` |
| `locqa report` | `report.json` | `report.html` | Пересобрать HTML без повторного запуска проверок |

**Главная команда, все флаги**

```
locqa check \
  --source data/intl_ru.arb \
  --target data/intl_kk.arb \
  --glossary glossary/glossary.csv \
  --out out/report.json \
  [--html out/report.html]
  [--context data/intl_en.arb data/intl_uz.arb]   # доп. контекст для LLM
  [--only untranslated,placeholder_mismatch]      # список проверок
  [--skip machine_translation_suspect]
  [--llm | --no-llm]                              # по умолчанию --no-llm
  [--llm-model NAME] [--max-llm-strings N] [--budget-usd X]
  [--min-severity low|medium|high]
  [--lang kk|uz]                                  # бонус: узбекский
```

**Принципы**

- без флага `--llm` команда работает полностью офлайн, бесплатно и воспроизводимо; это основной режим для тестов и CI
- `--budget-usd` и `--max-llm-strings` останавливают LLM-часть, когда лимит достигнут, и пишут об этом в отчёт
- один и тот же ввод даёт один и тот же `report.json` (стабильная сортировка, без случайности в правилах)

**Коды возврата** (нужны для GitHub Action)

| Код | Значение |
| --- | --- |
| 0 | Находок выше порога `--min-severity` нет |
| 1 | Находки есть |
| 2 | Ошибка ввода: файл не найден, битый ARB, неверные флаги |
| 3 | Ошибка LLM: нет ключа, превышен бюджет, сеть. Результаты правил при этом сохраняются |

## 6. 11 проверок: правило или LLM

Десять проверок делает код, нейросеть нужна только для `machine_translation_suspect` и для разбора спорных случаев других типов. Предложения исправлений (`suggestion`) тоже делает LLM поверх найденных проблем.


| # | Тип | Чем делаем | Алгоритм | Где ложные тревоги |
| --- | --- | --- | --- | --- |
| 1 | `untranslated` | Код | Ключ есть в `source`, но нет в `target`, либо значение пустое или только из пробелов | Ключи, которых сознательно нет в одном языке |
| 2 | `same_as_source` | Код + белый список, спорные в LLM | `target == source` после `strip`. Пропускаем, если в строке нет букв, нет кириллицы (латинские бренды) или строка в белом списке (имена, бренды, служебные символы) | Самая шумная: много интернациональных слов («Профиль», «бонус») совпадает законно |
| 3 | `placeholder_mismatch` | Код | Сравнить множества `{name}` в `source` и `target`. Так же сравнить теги вроде `<g>...</g>` и `\n` | Почти нет: правило точное |
| 4 | `plural_mismatch` | Код | Разобрать ICU `{n, plural, one{...} other{...}}`. Проверить баланс скобок, наличие `other`, допустимые формы для языка | Почти нет |
| 5 | `glossary_violation` | Код + глоссарий | Если в `source` есть термин из глоссария, в `target` должен быть его казахский вариант. Сленг («варн») даёт `low` | Казахский аглютинативен: концы слов меняются, нужно искать по основе, не по точному совпадению |
| 6 | `length_overflow` | Код | Только для коротких строк или ключей с признаками кнопки, вкладки, заголовка. Считаем `len(target) / len(source)` и абсолютную длину; пороги подбираем на данных | Казахский по норме длиннее русского в несколько раз; без учёта типа элемента получим тысячи лишних находок |
| 7 | `machine_translation_suspect` | LLM (после фильтра правилами) | Дешёвый предфильтр: русские слова внутри казахского, подозрительная длина, совпадение с `uz` или `en`. Потом LLM смотрит пару «русский + казахский» с контекстом | Самая сложная по точности: модель может придираться к живому сленгу |
| 8 | `inconsistent_term` | Код + глоссарий | Группируем ключи по одинаковому русскому тексту и сравниваем их казахские переводы; термины из глоссария ищем по основе и смотрим, какие казахские варианты встречаются | Одинаковый русский текст может быть в разном контексте и переводиться по-разному законно |
| 9 | `suffix_harmony` | Код | Регулярное выражение: плейсхолдер и сразу после него аффикс (`{name}-ға`, `{id}-ға`). Решение: переформулировать без аффикса после плейсхолдера или пометить «нужна обработка в коде игры» | Плейсхолдер с числом или названием, которое всегда одинаково заканчивается; но без знания игры этого не узнать |
| 10 | `orthography` | Код + словарь из данных | У слова есть похожий вариант с казахскими буквами (ә ғ қ ң ө ұ ү һ і), который встречается в файле чаще. Плюс латинские «двойники» внутри кириллических слов | Редкие легитимные слова и ники дадут шум |
| 11 | `wrong_language` | Код, спорные в LLM | Латинские маркеры узбекского (`o'`, `g'`, сочетания вроде `sh`, `ch`), совпадение строки с `uz` пословно, доля кириллицы без казахских букв в длинной строке | Бренды и английские названия в казахском тексте |

**Что не делаем.** Мы не правим строки автоматически ни по какой из проверок. Проверка находит, LLM предлагает, человек решает.

**Порядок разработки по выгоде.** Сначала «дешёвые и точные» (1, 3, 4, 9, 11), потом «с настройкой» (2, 6, 10), потом «через глоссарий» (5, 8), и в конце 7-ю через LLM.

## 7. LLM-слой

LLM решает только то, что не ловится правилами: насколько строка похожа на машинный перевод, спорные случаи других типов и текст исправления. Весь файл в неё не отправляем.

**Что модель получает в промпте**

- ключ и раздел из `@@comment` (частая подсказка контекста: название раздела игры)
- русский оригинал и текущий казахский перевод
- английский и узбекский варианты как дополнительный контекст (они уже есть в данных)
- термины из глоссария, которые встречаются в этой строке, вместе со сленгом
- несколько примеров «плохо / хорошо» от носителя (few-shot)
- соседние ключи из того же раздела, если у строки нет описания

**Что модель возвращает.** Строгий JSON с полями `Finding` (`verdict`, `issue_type`, `severity`, `confidence`, `evidence`, `suggestion`). Ответ проверяется схемой; если не прошёл, запрос повторяется один раз.

**Правила безопасности качества**

- LLM никогда не пишет в `intl_kk_fixed.arb` напрямую; только `suggestion` в отчёте
- плейсхолдеры из `suggestion` проверяются кодом: если не совпадают с русским, предложение отбрасывается
- `temperature` = 0, версия промпта записывается в `report_meta.json`
- кеш по ключу `(key, source, target, версия промпта, модель)`, чтобы повторный прогон не тратил деньги
- строки с низкой `confidence` не уходят в таблицу для носителя; они остаются в `report.json` с пометкой «low»

**Стоимость.** Каждый запрос логирует входные и выходные токены. В `cost.json` пишем модель, количество запросов, токены и итоговую стоимость; тарифы берём из конфига, не зашиваем в код. Итог попадает в HTML-отчёт и в описание методологии, как требуют организаторы.

**Выбор модели.** Клиент делаем так, чтобы провайдер менялся одним флагом и конфигом. Тогда можно сравнить 2-3 модели на одних и тех же строках и выбрать ту, которую носитель оценит лучше. Такой быстрый тест на 30-50 строках заодно отвечает на вопрос, нужна ли своя модель: если готовая с глоссарием даёт приемлемое качество по оценке носителя, обучение не нужно.

## 8. Исправления и проверка носителем

Носитель казахского это самый дорогой ресурс команды, поэтому процесс строится вокруг его времени. Оценивают 150 случайных изменённых строк, так что лучше менять меньше строк, но качественно.

1. `locqa check --llm` даёт `report.json` с `suggestion`.
2. `locqa review-sheet` выгружает `review.csv`: `key`, `source`, `target`, `suggestion`, `issue_type`, `severity`, и пустые колонки `decision` (`accept` / `edit` / `reject`) и `final_text`. Сначала идут строки с `high`, потому что у носителя ограниченное время; таблицу разбиваем на небольшие части.
3. Носитель заполняет `decision`. Даёт свой текст, если предложение машины не подходит.
4. `locqa apply` берёт только строки с `accept` или `edit` и пишет `intl_kk_fixed.arb`. Всё остальное в файле остаётся байт в байт.
5. Для каждой изменённой строки ставится флаг проверки человеком. В `report.json` у таких находок `reviewed_by_human: true`.
6. `locqa validate` проверяет итог.

**Что проверяет `validate`**

- плейсхолдеры в каждой изменённой строке совпадают с русским
- ICU-синтаксис корректен
- число ключей и их порядок не изменились, кроме добавленных переводов для `untranslated`
- файл собирается командой `flutter gen-l10n` (нужен Flutter SDK на одном из компьютеров; если его нет у всех, запускаем только у одного участника)

**Опасные места**

- `intl_kk_fixed.arb` не перезаписываем через `json.dump`: потеряем повторяющиеся `@@comment`, порядок и экранированные символы из private-use области
- строки с `suffix_harmony` нужно переформулировать так, чтобы аффикса после плейсхолдера не было; носитель должен утвердить новую формулировку
- массовую замену всех `suggestion` без проверки делать нельзя: команда `apply` просто не принимает строки без решения носителя

## 9. Тесты, CI, README и HTML-отчёт

Это покрывает критерий «универсальность» (15%) и часть «объяснимости» (15%). Нам нужно показать, что инструмент работает на любом ARB, а не только на нашем.

**Тесты (`pytest`)**

- на каждую проверку минимум три теста: найдено, не найдено, крайний случай
- тесты парсера: повторяющийся `@@comment`, экранирование `\n` и `\uXXXX`, пустые строки, дубли ключей
- тест «универсальности»: маленький синтетический ARB для другой пары языков (например `en` → `uz`), чтобы доказать, что ничего не зашито намертво под казахский
- тест CLI на коды возврата 0, 1, 2
- LLM-часть тестируем через подменённый клиент (без сети и денег)

**GitHub Action** (бонус). Запускается на каждый pull request, в котором меняются `*.arb`. Делает `pip install`, запускает `pytest`, затем `locqa check --no-llm` на изменённых файлах и загружает `report.html` как artifact. Реальные данные в CI не попадают, только фикстуры из `tests/fixtures/`.

**HTML-отчёт.** Один самодостаточный файл без внешних зависимостей. Сверху сводка: число находок по типам и severity, стоимость LLM. Ниже таблица с фильтрами по типу, важности и статусу проверки человеком. В каждой строке оригинал, текущий перевод, предложение, evidence и цветная метка severity. Так отчёт покрывает критерий «объяснимость» и работает как инструмент для носителя.

**README и документация**

- `README.md`: установка, быстрый старт на примере, список типов ошибок, ограничения
- `docs/SCHEMA.md`: форматы `report.json`, `glossary.csv`, `review.csv`
- `docs/METHODOLOGY.md`: как искали, как исправляли, сколько строк прошло через носителя, стоимость LLM

## 10. Этапы, роли и риски

Работа идёт от фундамента к надстройкам: написанное на каждом этапе должно работать само по себе и давать чёткий промежуточный результат. Только если этап готов, идём дальше.

| Этап | Что делаем | Кто | Готово, когда |
| --- | --- | --- | --- |
| 0. Договорённости | Схема `Finding`, форма `report.json`, флаг проверки, язык разработки | Вся команда | Схема записана в `docs/SCHEMA.md` и все с ней согласны |
| 1. Скелет и парсер | Репозиторий, `pyproject.toml`, ARB-парсер, `models.py`, пустой `locqa check` | Разработчик | Парсер читает все четыре файла и видит дубли `@@comment` |
| 2. Правила «дешёвые» | Проверки 1, 3, 4, 9, 11 + `report.json` | Разработчик | `locqa check --no-llm` выдаёт валидный `report.json` на реальных данных |
| 3. Глоссарий | Каркас `glossary.csv`, термины и сленг | Носитель + кто-то из команды | Есть минимум термины из задания: «фракция», «семья», Grand Coins, «бизнес», «варн» |
| 4. Правила «с настройкой» | Проверки 2, 6, 10, затем 5 и 8 по глоссарию | Разработчик | Шум в отчёте оценен вручную на выборке из 100 находок |
| 5. LLM-слой | Клиент, промпты, проверка 7, `suggestion`, `cost.json` | LLM-инженер | Тест на 30-50 строках оценён носителем |
| 6. Отчёт | `report.html`, `review.csv` | Четвёртый участник или разработчик | Носитель может открыть таблицу и пройти строки |
| 7. Ревью носителем | Решения по строкам, глоссарий дополняется | Носитель | Заполненные `decision` для нужного числа строк |
| 8. Исправленный файл | `apply`, `validate`, `gen-l10n` | Разработчик | Файл компилируется, у всех изменённых строк флаг |
| 9. Тесты и документы | `pytest`, README, METHODOLOGY, питч, бонусы | Вся команда | Новый человек может запустить проект по README |

**Роли (предложение, для обсуждения в команде)**

- Разработчик: CLI, парсер, правила, `report.json`, `apply`, `validate`
- LLM-инженер: LLM-проверки, промпты, `suggestion`, стоимость
- Носитель казахского: эталонные метки, глоссарий, ревью исправлений
- Четвёртый участник: HTML-отчёт, README, тесты, GitHub Action, питч

**Риски**

| Риск | Что делаем |
| --- | --- |
| Нет носителя казахского | Искать сразу: без него теряем качество исправлений и часть precision |
| Много ложных тревог в `same_as_source` и `length_overflow` | Белый список, пороги по данным, разбор образца вручную |
| LLM придумывает перевод похуже текущего | Носитель утверждает каждую строку; промпт с глоссарием и примерами |
| Файл не проходит `flutter gen-l10n` | Проверять сразу на первой правке, а не под конец |
| Данные попали в git | `.gitignore` с первого коммита; тесты только на синтетике |
| Ключи API попали в git | `.env` в `.gitignore`, `.env.example` в репозитории |
